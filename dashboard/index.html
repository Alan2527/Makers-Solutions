Cómo leer el rojo de esta suite. El caso API-02 falla a propósito. No es un error del código: es un defecto real de la API bajo prueba, que confirma la creación de un usuario con un 201 Created pero después no lo guarda. Está documentado como HALLAZGO-API-01. Se decidió dejarlo en rojo en vez de simular la respuesta: una suite en verde que oculta un defecto crítico no sirve para nada.

Alcance del módulo

El enunciado pide un conjunto mínimo de pruebas para validar el inicio de sesión. Los 3 puntos solicitados están cubiertos por estos 4 casos.

  • Los datos de prueba viven en archivos aparte (cypress/fixtures/): ninguna credencial está escrita dentro de un test.
  • Los localizadores usan atributos data-test y están centralizados en Page Objects: si la aplicación cambia, se corrige en un solo lugar.
  • No hay pausas fijas: se espera por condiciones concretas, lo que evita pruebas lentas y falsos rojos.

HALLAZGO-API-01 · La API confirma una creación que nunca ocurrió

Severidad crítica   Defecto de contrato · Estado: abierto

Explicado sin tecnicismos: es como cargar un cliente nuevo, recibir el cartel "Cliente creado con éxito, número 254", ir a buscar al cliente 254 y que el sistema responda "ese cliente no existe".

PasoPeticiónRespuesta
1 · CrearPOST /api/users201 Created  id: 254
2 · ConsultarGET /api/users/254404 Not Found  {}
ContrapruebaGET /api/users/2200 OK  usuario existente

Por qué es grave: el código 201 Created no es decorativo, es una promesa formal del estándar HTTP: el recurso fue creado y lo podés ir a buscar. Cualquier sistema que consuma esta API va a confiar en esa promesa. Un 201 que miente es peor que un error, porque un error se ve y esto no.

Causa raíz: reqres.in es un servicio de simulación sin base de datos. Eso explica el comportamiento pero no lo justifica: desde el punto de vista de quien la consume, la API responde mal, y detectarlo es exactamente el trabajo de las pruebas.

La decisión de diseño: por qué se dejó en rojo

OpciónQué implicabaDecisión
Simular la respuestaInterceptar la llamada y devolver un 200 falsoDescartada — deja todo en verde ocultando un defecto crítico
Validar el 404 y darlo por buenoEl caso pasa, pero valida un comportamiento incorrectoDescartada — convierte un defecto en el comportamiento oficial
Dejarlo en rojo y documentarloEl problema se ve y queda trazadoElegida
El criterio de fondo: una suite de pruebas no está para estar en verde, está para decir la verdad sobre el sistema. Un rojo explicado es información accionable. Un verde conseguido tapando el problema es una suite que da falsa tranquilidad — y el día que haya un defecto real, tampoco lo va a detectar.

Decisiones técnicas

  • Cypress + JavaScript — de las tecnologías permitidas por el enunciado, es la que cubre interfaz y API en un solo proyecto.
  • Page Object Model — los archivos de prueba describen qué se valida; los Page Objects, cómo se interactúa. Si la aplicación cambia, se corrige un solo archivo.
  • Datos en archivos aparte — ninguna credencial ni texto esperado está escrito dentro de un test.
  • Localizadores data-test — más estables que las clases de CSS, que cambian con cada retoque de diseño.
  • Sin esperas fijas — se usan esperas por condición, no pausas de N segundos. Evita pruebas lentas y falsos rojos.
  • Un reintento solo en modo automático — absorbe la inestabilidad de red en el servidor de integración sin ocultar fallos reales.
  • Integración continua — cada cambio ejecuta la suite y republica este dashboard y el reporte Allure.
